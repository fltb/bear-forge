## 上一轮决定（已被最新契约取代）

上一轮未能证明现有实现达不到目标，因此当时提出优先适配 Neil Fraser 的 JS-Interpreter，自研九节点 VM、CFG/显式帧代码生成不再作为默认实施任务。游戏 SDK、能力白名单、会话、策略与分析分层保留。原 execution/proofs 文档作为旧模型和行为契约参考，不是必须实现的指令集，也不证明第三方引擎正确。

这不代表后端已验收。旧 V8 块执行路线的性能假设不适用于 AST 解释器；在没有数据时，不能断言现成解释器必然过慢。

## 已有能力与真实缺口

| 需求 | JS-Interpreter 证据 | 结论 |
| --- | --- | --- |
| 保存变量、循环、闭包、流程位置 | 文档明确说明完整状态序列化 | 已有能力 |
| 原地暂停恢复、多未来分叉 | step 与序列化恢复；官方列出 fork 用途 | 可由薄适配组合 |
| 无历史重放恢复 | 恢复器重建对象图与解释器字段 | 已有路径，需重绑定原生能力 |
| 结构共享/COW | 所查序列化器遍历对象并重建 | 此路径非增量分叉；是成本缺口，不是功能不可能 |
| TS 编写 | 执行 ES5，可用标准 TS 下编译 | 必须定义语法和标准库 profile，不支持任意 TS |
| 宿主状态受控 | 原生函数按初始化实例内的 ID 重绑定 | 对局状态不得藏于原生函数闭包，白名单继续保留 |
| 确定随机/时间与记录 | 需 SDK 与内建能力管控 | 属于适配工作，不需要新语言引擎 |
| 训练负载速度 | 本项目尚无实测 | 未知，不能作为排除理由 |

依据：[官方文档](https://neil.fraser.name/software/JS-Interpreter/docs.html)、[仓库](https://github.com/NeilFraser/JS-Interpreter)、[序列化源码](https://github.com/NeilFraser/JS-Interpreter/blob/master/demos/serialize.js)。源码恢复分为创建对象和恢复引用两遍；原生函数从初始化解释器查找。序列化依赖未压缩内部 API，需固定解释器、Acorn、序列化器兼容版本。此次获取部分源码但未成功解析提交号，不声称已锁定依赖。

## 其他候选

- [Stopify](https://stopify.readthedocs.io/en/latest/compiler.html) 已实现 JS 到 JS 控制流变换。暂停不自动证明整个堆可序列化并隔离多次恢复；资料不足以认定它完整适配，也不足以断言做不到。
- [quickjs-wasi](https://github.com/vercel-labs/quickjs-wasi) 保存 WASM VM 和待决 Promise，恢复到新实例，原生回调需重新注册。文档中断接口抛异常，不提供从被中断指令原地续跑的保证，不能无声替代我们的预算让出语义。它不是原生进程 forkserver，当前不选为默认后端。
- [OpenSpiel clone](https://github.com/google-deepmind/open_spiel/blob/master/docs/api_reference/state_clone.md) 复制已建模的游戏状态，不能据此推导它自动捕获任意 TS 调用现场；可复用上层接口思想，但也不能据此声称它无法实现同样游戏。

## 薄适配实现方向

```text
TS 源码＋类型声明＋传递依赖白名单
  → 标准工具下编译到批准的 ES5 profile
  → JS-Interpreter
  → RuntimeAdapter：advance / snapshot / restore / fork / submit
  → 原 SessionService / PlanningService / ExperimentService
```

TS 降级不自动补齐 Promise、Map 等运行时库。旧 async 示例不能直接声称兼容。首选桥接提案为客体同步风格 choose：请求和应答槽位保存于客体堆，宿主在 step 边界观察到请求后停止 stepping，合法响应写入槽位再继续。桥接需实现与边界验收，但无需自己捕获调用栈。现有 async authoring API 保留待适配，不能把宿主 Promise 回调当作可序列化续延。

游戏数据、请求、随机状态、必要日志均在客体状态或显式关联的会话快照中。原生能力只允许纯操作/受控端口，不保存游戏局部变量和剩余流程。观察与受限模拟权限继续由游戏/服务层负责。

fork 第一版可将同一快照恢复到多个独立实例，不宣传 O(1) 或 COW。若以后测得瓶颈，先定位序列化或解释派发，再比较已有后端与局部改造，不默认回到自研。

## 代码量与性能预算补充

2026-10-08 下载官方 master 原文件统计：interpreter.js 5023 行/171426 bytes，acorn.js 2289 行/75382 bytes，demos/serialize.js 525 行/15296 bytes，合计 7837 行/262104 bytes。为物理行数，包含注释空行；不含测试、示例、压缩产物等，不称作整个仓库 SLOC。后续版本会变化。

自研估算为规划区间，非根据行数推导工期：仅九节点参考执行器约 0.5–1.5K 行，不构成可用作者系统；受控 TS + 可用执行后端整体约 7–20K 手写实现行，另约 5–15K 测试。包括执行/帧 1–3K、存储快照 1–3K、SDK 0.5–1.5K、TS 转换与准入 3–8K、源码映射/错误/边界工具 1–3K。复用路线仍需约 1–3K 适配/profile/SDK 实现及约 2–5K 测试，复用两条路线共需的游戏、会话、策略层不计。范围随支持语法和隔离要求改变，不能按 AI 生成速度保证交付。

源码显示 JS-Interpreter 按节点类型派发，维护 State 对象与作用域；V8 优化的是解释器实现，不会直接将客体规则作为普通 JS 函数优化。因此预计规则纯计算明显慢于直接 V8 执行，但无可靠本项目倍数。step 公共调用可能还包含内部 polyfill 推进，不能把一次 step 等同一个固定成本节点。

性能需分拆为内部转移工作/秒、每决策转移数、原生操作成本、投影日志和分叉频率。若一决策内部转换为 1K/10K/100K，要压到 1ms，仅转换就需 1M/10M/100M 次每秒；其余开销另加。这是需求算术，非测得吞吐。快照遍历/重建成本随可达对象图和属性数增长，不能只依据序列化后的字节数估恢复时间。

功能上可复用不等于性能已合格；目前维持复用优先，但不再给此后端沿用 V8 块执行的 1ms/决策预测。普通推进不要求每个决策都做完整序列化，只有保存/搜索分叉时才支付该成本；搜索工作量应单独预算。
