# 4070 本地：执行器、模型与通信预算

状态：条件算术和设计门槛，不是引擎/4070 实测。现有方案没有可测的游戏实现。以已有桌面 4070、8 个 CPU worker（须有相应可用 CPU 资源）、有效并行效率 50% 为例。

## 模型预算

5M 参数、128 个输入 token、4 次 PPO 样本更新、共享策略价值主干。每次真实决策包括一次采样推理和四次学习前反向：

```text
推理粗算 = 2PL = 1.28 GFLOP
训练粗算 = (2 + 6E)PL = 16.64 GFLOP / 新决策
```

这是参数矩阵计算近似，未精确计入二次注意力、逐 token 动作解码、额外前向、优化器和小算子开销。PPO 分块训练不能跨更新错误复用旧隐藏表示。有效吞吐 5–20 TFLOP/s 仅是敏感性参数，非 4070 保证：分别对应训练 3.328–0.832 GPU 毫秒/新决策、推理 0.256–0.064 GPU 毫秒/决策。批量摊销时间不等于单请求延迟。输入增长不能为预算而截断必要合法信息。

## CPU 预算

每个决策的 CPU 工作包括内核推进、游戏逻辑、投影、合法动作、编码和必要日志。令总耗时 t_env，worker 数 W，有效效率 eta，容量约 W*eta/t_env。

| 单决策 CPU 耗时 | W=8、eta=0.5 的容量 |
| --- | ---: |
| 0.1 ms | 40000 决策/秒 |
| 1 ms | 4000 决策/秒 |
| 5 ms | 800 决策/秒 |
| 20 ms | 200 决策/秒 |

理想充分流水时总吞吐受最慢阶段限制；同步 PPO 收集/更新阶段还有不可重叠时间，实际不得直接取各阶段容量最小值作为保证。p95/p99、长结算和 GC 导致尾部等待，也要记录。

首轮工程目标：平均环境+编码不超过 1ms/决策；若 5ms 以上已可能明显制约小模型训练；若 20ms，则先解决环境侧问题。这些是当前模型预算下的门槛，不是语言基准。

### JS 后端的具体预算与可承受范围

这里的 JS 指生成的同步块函数 + 显式帧/context，不是逐 AST 节点解释、不使用每条内核指令一个原生 Promise。无游戏实现和目标 CPU，不能给出有测量依据的 JS 耗时预测。

以每决策 1ms 为设计分配：规则与派生计算 0.5ms、帧/状态管理 0.2ms、合法动作与观察编码 0.2ms、必要记录与摊销 GC 0.1ms。这是验收预算，不是这些模块已达到的性能。复杂度取决于每决策内部步数、事件连锁长度、扫描次数、复制字节数和分配对象数；不能由卡池大小直接推算。

仍取 8 个真正并行 CPU worker、50% 效率。用不重叠相加近似总时间：每决策 CPU 摊销 t_env/4 + GPU 0.83–3.33ms + 通信调度摊销 0.1ms。通信值也仅是假设，不含任意长凑批等待。30M 新决策：

| JS 环境+编码平均耗时 | CPU 供给容量 | 30M 决策计算时长情景 |
| --- | ---: | ---: |
| 0.5ms | 8000/s | 8.8–29.6 小时 |
| 1ms | 4000/s | 9.8–30.7 小时 |
| 5ms | 800/s | 18.2–39.0 小时 |
| 20ms | 200/s | 49.4–70.2 小时 |

这是简化流水预算，不是速度上下界或学习收敛保证；显存、CPU 型号、训练实现、尾延迟和模型序列长度都会改变结果。不含独立评测/调参。单 Node 线程无法获得 W=8 的吞吐，多个 Promise 也不构成 CPU 并行；需要 worker threads 或进程，受控游戏现场仍由 VM context 管理。CPU 资源不足时按实际 W*eta 重算。

在当前本地试跑规模下，平均 5ms 甚至 20ms 不会自动使训练不可行，只会延长运行。是否迁移语言应根据热点归因；减少重复扫描、对象复制、序列化往往应先于重写执行后端。

## 通信预算

每个观察假设 128 个实体槽位，每槽 16 个 int32 字段，约 8KiB；返回动作几十字节。只传合法观察、mask、动作及训练元数据，不传完整 context，不在 CPU 展开 embedding。

2000 决策/秒只需约 16.4MB/s 上行。假设实际 H2D 带宽 8GB/s，64 个观察为 512KiB，纯复制约 65.5 微秒/批、1.0 微秒/决策。此数未包含 IPC、编码、分配、驱动启动、D2H 同步及等待凑批，不代表实测端到端延迟。

[NVIDIA 指南](https://docs.nvidia.com/cuda/cuda-c-best-practices-guide/index.html) 建议合并小传输及合适使用 pinned memory。[PyTorch 指南](https://docs.pytorch.org/tutorials/intermediate/pinmem_nonblock.html) 提醒临时 pin_memory 可能抵消收益，且异步 D2H 读回前必须正确同步。

接口以批量二进制为先，可从批量 pipe/socket 起步；仅在测得 IPC 占比显著时增加共享内存 ring buffer。复用训练器侧 staging buffer，按实际 API 设置锁页与异步复制；JS SharedArrayBuffer 不能自动当作 Python 或 CUDA 的零拷贝内存。

建议批量 32–128，并以截止时间发出不足批次。4–8 个 worker 各可保存多个显式等待 context，使可并行游戏数高于 CPU worker 数。batch 不得等待比活跃 context 更多的请求。每个会话有序，跨会话合批；记录行为策略版本，PPO 更新边界控制策略滞后。自回归动作参数尽量在 GPU 上一次生成完，仅真实游戏选择边界回 CPU。

## 执行位置决策

当前采用 CPU TS 游戏执行、GPU 模型和张量计算。不将通用规则解释器搬上 GPU：分支发散、可变队列、动态数据和历史访问难以按当前表示高效批处理，迁移也会竞争模型显存和计算。未来可为规则结构固定的游戏增加专用批量后端，但必须通过同一语义验收，不能将此视为免费减少通信。

Rust 不是 PCIe 通信优化。只有定位到 CPU 热点后，才评估原生数据结构、批量编码或完整执行后端。现有编译输出含同步 JS 块与批准 TS 纯函数，Rust 不能直接执行；仅搬调度循环会频繁回调 JS，未必收益。完整 Rust 后端还需明确这些计算的共同 IR、批准的原生实现或运行边界，并作语义一致性验证，不暗中引入另一个语言子集。

优先避免整份 context 深拷贝、逐指令完整快照、逐对象 JSON/IPC、重复全局扫描；在不破坏快照与分叉隔离的前提下采用结构共享/COW、紧凑帧、增量记录和游戏索引。当前编译器禁止的跨写入融合不能以性能优化名义直接开启。

诊断必须分别记录：规则执行、投影编码、IPC、H2D/D2H、批等待、GPU 推理与更新、日志/GC。先看墙钟分解而非只看 GPU 利用率。若环境 CPU 已小于端到端时间 10%，即使无限加速该部分，总加速也不超过约 1.11 倍。
