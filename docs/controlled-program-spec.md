# 受控程序规范

## 受控对象

Core 接受经过准入的程序与全部传递依赖。Instance 拥有该程序的完整执行现场，包括调用栈、局部变量、闭包环境和对象引用图。游戏作者使用 TS 纯计算和 IO.call；不手工编写 PC，不将任意宿主函数注入规则计算。

## 准入边界

采用构造白名单及白名单内部排除规则。依赖图必须封闭；动态导入、eval、Function、宿主对象、环境全局变量与未声明的外部状态不能进入受控计算。真实时间、外部随机熵、网络或用户输入通过声明端口进入；显式 seed 驱动的伪随机计算可以在受控程序内执行。冻结常量与受控局部可变数据可以使用；影响执行的可变模块状态必须实例隔离并纳入现场，不能在实例间共享。

函数、递归与闭包在内部可以存在。跨端口的数据由各端口 schema 声明，不允许把指向活执行对象的引用泄漏给宿主。request.respond、observe、projectEvent 及可选 session 处理器同样受依赖与副作用检查；TS readonly 和 linter 不能独立证明纯性。

## 调用与恢复

一个稳定 Instance 挂起一个外部调用。程序须顺序等待受控调用；多个外部参与方通过显式事件输入协议表示。不得存在未受控的异步任务或脱离现场的效果。循环与递归的后续计算必须可保存；仅持有原生 Promise 不是可持久化现场。

端口返回经过当前声明检查后才能被接受，接受一次后继续执行。外部 bind/run 只有一个活动驱动租约；回调显式 reply/pause，取消撤销租约，迟到返回不能接续其他实例。稳定回调等待点可保存/分支，但宿主 Promise、AbortSignal 和绑定表不进入快照。错误返回不改变现场；执行故障结束该 Instance 的程序推进。运行预算故障不代表游戏输赢。保存只针对稳定调用或正常结束边界，运行中或故障的半现场不作为正常快照。

## 数据与 schema

固定类别用枚举/字面量；动态引用和游戏输入由对应 schema 定义。边界 schema 保持值，不使用 transform、coerce、default、catch 等隐式变换。显式游戏适配函数可以转换数据，但每次转换必须有声明的输入与输出契约。对象参数与返回隔离，禁止访问器、宿主资源和共享可变缓冲区跨界。

tests/support/schema-admission.ts 是正式测试使用的辅助代码，用于验证固定结构、显式批准的检查回调及边界值隔离。C02 的生产准入与执行实现需保持对象别名、闭包和控制现场的语义。

## 原生差分

ProgramModule.run 可直接由 V8 调用，IO 由测试绑定提供。同样的 setup 与外部调用返回序列下，原生和受控程序的可观察调用/结果轨迹应一致。NativeCoreLoader 与 ControlledCoreLoader 具有同一外部 Core 形状；原生提供者不必具备完整保存能力。原生游戏及逐玩家消费者在 C01 验收，受控后端和双端轨迹对照在 C02 验收。

## 服务与快照

Core 不内置随机或游戏时钟。内侧 SDK/设备库在 program.run 内创建，其闭包与可变局部属于 Instance。外侧 BaseGame 只能有可重建缓存，不另存随机流、输入封存或事件发布进度。PortBindings 可提供真实外部输入；这不授权把游戏内部状态藏进宿主函数。保存与分支只处理 Instance，未来外部回复由调用方显式提供。

## 实施验收

后续 C02 必须验证：嵌套循环/递归/闭包等待点保存；双分支隔离；不靠完整重放恢复；白名单覆盖依赖；外部输入与随机服务可回放；预算、故障与正常完成区分。C01 的协议、作者包和消费者测试提供上述验收的输入契约。

## 内侧库准入

`@bear-forge/game-sdk` 是程序依赖，不是宿主能力提供者。createGameSDK 仅以 IO 和已声明端口建立同名函数，捕获固定端口键和该实例 IO，不捕获外侧 GameContract 处理器。依赖白名单覆盖该包及全部传递依赖；当前包只有公开类型依赖，没有运行期依赖。端口声明为普通自有可枚举数据属性；动态构造、隐藏属性和访问器不得绕过固定端口表准入。冻结方法表不替代 Instance 的数据隔离和续延保存。原生差分允许直接使用同一库。
