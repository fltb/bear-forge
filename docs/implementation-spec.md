# 完整实施规格

本文规定 Bear Forge 从现有协议到首版完整系统的实现方案。公共协议以 `packages/contracts` 和 `protocol.md` 为准，不修改字段、方法、枚举、导出路径或行为。本文中的策略、实验、存储与分析接口属于上层模块，不加入 contracts。实施进度只记在 `plan.md`。

执行表示必须符合 requirements.md R03/R04：共享 Program + 独立 Context，仅在外部 call 及正常终局保存。Effectful 适配已拆分静态代码注册和实例初始化；fork/restore 只处理 Context。实现及验收状态见 plan.md。

最新 STS/Card Core 整体优化按[第23节](#whole-stack-optimization-implementation)实施；覆盖旧章节中冻结这项性能工作的阶段安排，不授权 Rust 迁移或重启训练研发。

## 1. 交付与完成标准

一次性交付可以实际运行的系统：游戏规则 → 玩家策略 → 多局实验 → 卡牌替换干预 → 领域事实 → 条件关系与证据界面。中间关卡是内部实施顺序，不是要求用户逐关重新授权。此次写 spec 不等于以下模块已经实现。

首版包含：

- 普通原生游戏运行，同一 Node runtime 内执行规则、SDK、BaseGame 和脚本策略。
- 受控编译、依赖准入、执行预算，以及完整现场的保存、恢复和分支。
- 正式接入现有完整斗地主；补充一个明确版本的可构筑实验游戏。
- RandomLegal、FirstLegal、LastLegal、一个游戏规则策略；独立策略记忆、固定版本、多人会话。
- 批量调度、持久化、重试去重、轨迹与领域事实、固定策略替换干预。
- 条件对局关系、替代、交互效应、覆盖与不确定性；证据查看和可重复运行的 CLI。

后置：神经网络优化器/PPO 训练、模型推理合批、自动脚本演化、玩家搜索产品、完整商业游戏复刻、云部署及正式多人运营。保存/fork 及搜索所需的边界验证包含在本次交付；不将后置能力宣称为已经实现。

完成要求：从干净数据目录执行登记命令，生成真实对局和关系数据；另一组冻结输入能复现语义结果；完整检查通过；终态、故障、截断、缺失和未知严格区分。

## 2. 功能归属与实现约束

| 功能 | 落实位置 | 禁止的替代方式 |

领域记录由游戏产生。capture 只提供通用调用历史，不能自动解释伤害、机会或卡牌关系。假设世界由游戏构造；fork 原样复制完整现场，搜索树与分支评价属于调用方。

## 3. 技术栈与模块

已有：TypeScript 7.0.2、Zod 4.6.5、@types/node 26.6.5、npm workspaces、Node test runner。新引入的依赖采用实施当天 npm `latest` 对应的稳定版，使用精确版本和 lockfile；不自动安装预发布版。升级必须通过正式检查，不能静默改协议来消除类型错误。

宿主使用 Node.js 最新稳定版；实际支持的最低版本由所选 API 和 CI 验证决定。现有 engines 下限不等于所有后续模块均已经支持该版本。实验结果及恢复进度使用本地文件保存，不引入数据库；公开执行协议不依赖具体存储格式。

界面使用 React + Vite + TypeScript；图使用 Cytoscape.js，样本与精确指标使用表格。服务使用 Node HTTP 与只读查询 API；首版绑定 localhost，暂停/运行等可写操作只能通过明确的调度入口，不给浏览器直接暴露 Instance。

## 4. 两种执行路径

### 原生路径

NativeCoreLoader 装载 ProgramModule，start 创建独立运行现场，run 通过宿主回调接受一次返回。IO.call 挂起本实例的 Promise；事件立即入队确认后可以继续运行。多个独立实例可处于同一 Node runtime。端口逻辑边界不要求跨进程、序列化或存档。

原生路径可以使用同一份游戏程序和 SDK。直接装载的 `ProgramModule` 是受信任的本地函数：闭包、模块状态及宿主调用照普通 JS 执行，作者负责避免不期望的跨局共享；Core 不声称检查其传递依赖或强制 IO-only。原生构建产物另做源码准入、模块工厂重建和可插桩预算，但保留 V8 原生 async/await/Promise，也不承诺 IO-only。两种原生入口的端口边界仍须值隔离、检查 schema、阻止旧租约回复。Native Promise 不作为可持久快照。

实验若提供原生构建产物，就装载该产物；没有原生产物时，原生任务使用游戏提供的可信 `ProgramModule` 直传。实验将所选执行内容绑定到登记身份；身份检查不等于 IO-only 证明。选择受控执行时必须提供受控产物。

原生构建入口只接收经过准入的本地源码，可在编译阶段插入有限工作量计数器；直接装载函数没有这项检查或预算保证。原生路径的实例在主 runtime 内运行，构建产物执行预编译模块工厂；受控路径按共享 Program 创建 Realm，不按 Instance 创建。不提供硬超时；无法插桩的原生调用等待返回。原生路径不承诺保存/fork，也不承担运行任意恶意 JS 的职责。

### 受控路径与选型关卡

受控路径采用提前编译、运行时装载产物的方式。现有实现使用 **Babel/Rollup + 修改后的 EffectfulJS core v2 续延转换**；已记录的上游反例已有修复，当前验收针对仓库内实际实现。原定目标是把顺序 async/await 转换成显式续延和可保存环境，生成 JavaScript 由 V8 执行。运行时不解释作者 AST，也不再做 TS/Babel 转换；不要求作者手写 PC。完整的编译阶段、实例模块工厂、端口适配和差分验收见 [compiler-and-differential-spec.md](compiler-and-differential-spec.md)。

此库提供可访问的 async 控制状态和序列化接线，不直接提供完整 Core/Instance。本项目已提供依赖准入、确定性调度、实例隔离、预算、静态构造器注册和跨进程持久快照；完整验收状态见 plan.md 顶部。未决宿主 Promise、活动回调和默认事件循环不能成为保存机制；Zod/SDK 的实际可达代码与闭包必须验收。

初期核对发行元数据时发现 workspace:^ peer 引用问题；当前采用仓库内带来源与许可的依赖分支，已落实发行/构建适配及 Babel 接线，不再将首次安装作为待办。现已通过通用程序和完整斗地主的编译执行与恢复测试；完整关卡仍以最终正式检查为准。首选路线不通过时报告具体反例与替代编译工作量，不退回解释器、不降低需求、不修改冻结协议。

同源原生/编译产物差分必须覆盖完整逐调用轨迹、最终结果、通用语义与算法 benchmark、SDK/Zod、完整游戏，以及每个稳定点和独立进程恢复、双分支隔离。详见补充规格；不能仅以游戏胜负一致证明编译正确。

### 编译产物、准入与预算

构建入口接收源码入口与配置，输出现有 CompiledProgram 的 content。content 内部封装程序/模块身份、引擎与编译版本、schema 身份、白名单策略版本、source map 和执行内容；格式是实现细节。装载器验证一致性、结构和大小，不将 Uint8Array 品牌当可信证明。

白名单覆盖所有可达运行期依赖和工具生成代码：未知构造、动态导入/eval/Function、宿主全局、网络、真实时间/熵、共享可变缓冲、访问器跨界均拒绝。库批准基于确切版本和可达代码，不按包名整体放行。schema 诊断和检查回调同样审查。错误不进入全局未处理 Promise rejection。

预算在 loader 的工厂配置中提供，不改固定 run 参数；每个实例独立计费。声明 step/堆内存/宿主截止时间/总决策限制的不同含义；运行预算终止返回现有 budget_exceeded，实验归类为 truncated，不能当输局。受控步数可重复；墙钟只用来防止失控，不用于要求确定的语义实验。

## 5. 完整现场和生命周期

稳定点只在端口等待或正常结束。快照编码 Context，包含跨边界必要的控制位置/显式帧、局部值、闭包捕获环境、对象引用图、模块可变状态、随机流、SDK 状态、待决调用或终局；另关联协议要求的记录前缀。静态代码、不可变元数据和模块导出容器不作为快照根。共享引用、循环对象图与原型语义按准入范围保持；内部对象图不能采用会丢失别名的普通 JSON 深复制。跨端口允许的数据范围与内部现场表示分别检查。

外部回调、AbortSignal、网络、策略记忆和活动驱动租约不保存。等待宿主回复时先在线性化点冻结待决调用与前缀，再完成序列化；不能持有宿主 Promise 的回调引用作为恢复机制。

restore/fork 创建新实例身份，保留保存的 CallId 和前缀，清空绑定。快照引用保存到检查点文件中，引用对应的内容也须持久保存，只有 reference ID 落盘不算恢复。restore 不重新运行已完成规则或外部输入。兼容性由提供者校验；进程重启后重新装载对应产物，再解析持久快照引用。

当前 fork 使用 COW 共享 Context 根，不遍历完整状态，首次推进也不能补做全量复制；后续写入只复制受影响的索引路径或内存页。直接复用已加载 Program，不重新执行程序或依赖初始化，不走字符串存档往返。关闭与 release 按现有契约保留有效子实例、快照及记录引用。可重建的 BaseGame 缓存不存入游戏现场。game.save 使用持有的句柄，恢复必须经 persistence.restore → binder.bind，不能从 BaseGame 私取 Instance。

## 6. 正式游戏接线与会话

game-host 独立实现 binder/适配器，不导入 tests/support。绑定前核对端口表、类别、schema、contract 准入及实际能力，再 transfer 接管；失败清理接管的实例。多个回调竞争、accepted、取消、事件重交付、纯投影故障、终态和 busy 全部依 protocol.md。

玩家只收到自己的 Request/onEvent。inspect 是调度能力，不传给策略。事件回调负责接收或入队，动画不阻塞权威规则。事件批次允许游戏成批发布；exact 完整枚举，construct 的生成/排序由游戏自己的动作适配负责。

真人会话先按到达序列入队，再通过回调交付。游戏要求 timeoutFirst 时，会话先只允许控制回调交付相应时钟/超时，run 返回后再处理玩家输入；不依赖 Promise 调度碰巧满足优先级。训练/实验用显式虚拟时间。网络重试由外层逻辑提交身份查询结果，不把过期 RequestId 重写成新请求后自动接受。

每局使用固定 game/rules/contract/strategy 版本。request、合法动作和错误消息都须通过隐藏信息反例；observe 和 options 不能透露本来不可知的状态。

## 7. 策略、轨迹与未来搜索

上层 Policy 定义 decide(request, visibleHistory, memory, localRandom, signal) → 候选 action、nextMemory、采样元数据。对外只将 action 包装成 CallbackReply。元数据含 policyVersion、encoderVersion、完整动作 logProbability（有概率时）、策略随机流前后位置；确定策略可不声明概率，不能伪造模型概率。

同一 player 的多个并发请求使用同一已提交记忆读视图，按 RequestId 暂存各自候选；仅 accepted 对应候选允许提交 nextMemory 和随机推进。失效/失败/暂停/竞争输掉的候选丢弃。事件记忆按玩家实际可见事件有序更新；accepted 动作、后续事件和提交次序要有明确测试。外部模型调用可以投机产生费用，但不能让未接受候选改变已提交策略状态。

基础策略按游戏声明的动作顺序消费 exact；RandomLegal 均匀采样合法语义动作，First/Last 使用相同规范顺序。construct 必须提供游戏专用 sampler/排序或候选生成器，不假定存在通用均匀分布；不支持的策略组合在任务登记时拒绝。

奖励由游戏训练适配计算。轨迹保存实际传给策略的请求与可见事件，不拿 capture 的完整 view 充当 observation。按玩家、逻辑决策、动作类型关联；会话控制不计作玩家选择，默认超时动作与策略行为区分。终局、截断与故障不使用同一奖励结束标记。

搜索后续独立实现：游戏从合法观察/历史构造可能世界，复用同一规则；搜索模块 fork/绑定动作/模拟/评估，返回普通 action。首版仅验证接线与信息边界，不交付 MCTS。真实现场分支仅向明确的分析实验开放。构造器须表达未完流程，不能假定只复制场面即可。事件序号、种子和错误诊断不作为偷偷获取隐藏信息的途径。

## 8. 可构筑实验游戏

斗地主保持完整现有规则。新增 `forge-duel-v1` 作为首版有限卡池研究游戏，明确标注为研究规则，不冒称商业游戏；以下为本 spec 的实施默认，规则实现前形成独立 game 文档和 schema，版本固定后不得在同一实验中变动。

双人轮流行动，生命20；每副12张、同名最多2张；开局各抽3张，无调度。起手玩家由 setup 指定。每个自己的回合开始：最大法力+1（上限6）、补满法力、抽1张、恢复已有单位行动资格。每方每局自己的回合上限30；第30回合结束仍无人获胜为正常规则平局。外部计算预算耗尽则是截断。

场上最多4个单位，手牌上限8；超上限抽到的牌公开弃掉。空牌库抽牌受到递增疲劳伤害（第一次1，之后每次+1）。单位进入场上本回合不能攻击；每单位每回合攻击一次，单位战斗同时造成攻击力伤害，双方死亡一起移出。守卫存在时不能攻击对方英雄或非守卫单位。英雄生命≤0立刻结束，同时为0平局；回血不超过20。不存在响应窗口或未声明的隐式优先级。

| 卡牌 | 费用 | 完整效果 |
| --- | --- | --- |
| 斥候 | 1 | 单位2/1，无附加效果 |
| 守卫 | 2 | 单位1/4，守卫 |
| 猛兽 | 3 | 单位4/3，无附加效果 |
| 见证者 | 3 | 单位2/3；在场时每当另一个友方单位死亡，英雄回复1；同批死亡中见证者也死亡则不触发 |
| 火花 | 1 | 对任意敌方目标造成2伤害 |
| 爆裂 | 3 | 对任意敌方目标造成4伤害 |
| 补给 | 2 | 连续抽2张，逐张处理疲劳/手牌上限和终局 |
| 修复 | 1 | 英雄回复3生命 |

动作只有出牌（实体ID、必要目标）、攻击（实体ID、目标）、结束回合。目标存在、费用、手牌、场位和行动资格必须同时合法。每个实体入场分配新游戏ID，事件由游戏给出稳定事实键。每一步立即处理死亡/终局；事件中含因果动作键，完整合法动作枚举由独立 oracle 核对。

游戏 view 是完整边界数据；observation 仅含自己手牌、双方公开场面/弃牌/牌库数量和可见历史。对手牌库顺序及手牌隐藏。game analysis adapter 可以消费完整事件以计算机会，玩家策略不能消费此数据。

基础构筑：斥候×2、守卫×2、猛兽×2、见证者×2、火花×2、补给×2。替换实验：将指定一张火花替换为爆裂，费用差是干预内容；其他牌、策略代码、座次分布和采样方案固定。挑战构筑由预先登记的合法配方组成，不能在确认集结果出来后挑选有利对手。

规则策略：枚举合法动作，按当前合法观察评价即时击杀、交换、单位/法力利用和终局，使用确定权重与规范次序打破平手；复用原规则的纯评价辅助，不另建一套结算引擎。策略版本冻结，替换后仍使用相同代码，不声称这是策略适应后的最优强度。

## 9. 游戏事实与实验登记

游戏提供 analysis adapter：把自己的完整事件/终局解释成领域事实；fact 键、cardDefinitionId、cardInstanceId、actor、回合/逻辑动作、原因与数值语义由游戏定义。至少输出携带、抽到、可用、使用、目标、效果和结果。

机会分母固定：携带按开局卡数；抽到按实际进入手牌实例；可用按逻辑玩家决策中存在至少一个该牌合法出牌动作；使用按已接受输入产生的实际出牌事实。同一请求因暂停重试不重复计机会；时钟控制产生的新 callId 不自动等于新的玩家机会。游戏提供领域决策键/规则，不能直接按通用调用次数计数。

实验配置含规则/产物/适配/策略版本、构筑、座次、显式种子集合、虚拟时钟、预算、对手集合、干预、指标、最小有意义差异、发现/确认划分、停止条件。setup 通过游戏工厂生成；未声明构筑或干预直接拒绝，不能给 Core 加通用 deck 字段。

初始默认登记：四个策略，基础/挑战构筑，两个座次，128个发现种子块、128个独立确认种子块。执行前 CLI 展示实际任务数和预算。种子块内对照/干预共享初始随机配置并交换座次；替换后随机路径可能分歧，不宣称两世界抽到相同卡或完全共同随机数。

全部任务按预算运行；失败不补成零值，重试不生成新独立样本。探索途中预算用完，输出部分覆盖与未知，不自行申请付费算力。

## 10. 存储、回执与故障恢复

实验持久化采用本地目录：快照由现有文件快照提供者保存；每个任务提交一个完整的版本化文件，包含进度、策略记忆、轨迹、领域事实和结果。先写临时文件并同步，再原子替换任务文件并同步目录。提交前的数据不作为实验样本；重启读取已提交任务文件。单机单调度器写入，默认串行、可登记1–4局并发，不引入数据库、SQL 或独立消息服务。

| 文件内容 | 身份与用途 |
| --- | --- |
| artifacts | artifactId；可重新装载的内容、schema/引擎/规则版本 |
| experiments / tasks | experimentId / taskId；登记条件、冻结输入与完成状态 |
| attempts | attemptId；重试编号、故障/预算与实际开销 |
| checkpoints | checkpointId；游戏快照引用、策略记忆、随机流、会话、记录截止位置 |
| snapshots / snapshot_refs | 内容与引用；释放一个引用不破坏其他引用 |
| commits | commitId；每 task 的唯一递增逻辑步、前后检查点及接受事实 |
| packets / decisions / deliveries | 实际可见请求、候选/接受、玩家事件与交付去重 |
| facts / outcomes | 游戏领域事实、终局/截断/故障；关联 task/commit |
| lineage | 父子任务/检查点及前缀截止位置，区分重试与独立分支 |
| estimates | 分析配置、条件、样本引用及计算结果，可重算 |

taskId 由冻结实验条件标识，attemptId 只区分重试；commitId=(taskId,logicalStep)，唯一任务/步骤身份防重复。RequestId 是实际运行凭证，恢复后不能作为稳定业务提交键。候选回复保存原始凭证；恢复重试只能由调度方重新读取请求、重新绑定已经登记的逻辑输入，不能让客户端旧凭证直接生效。

原生任务默认整局提交：先持久登记 task；跑完后一次文件提交写轨迹/事实/结果与 task 完成标记。崩溃重跑未完成整局，文件提交失败不发布部分样本；无需每步保存游戏。

要求中途恢复的任务采用受控路径：先持久保存旧检查点；执行一逻辑输入、收集 accepted 与可见事件、保存新稳定现场；随后把已持久新快照的引用、暂存策略状态、轨迹/事实/提交回执和 task 指针放在同一检查点文件中原子提交。事件回调只入本轮暂存队列，提交后通过已提交文件的只读查询对外发布；不能先发不可撤销结果再声称可回滚。

若停止在 event 暂停边界，保存该稳定现场和已接收入队的批次信息；按游戏稳定事实键/逻辑检查点及玩家去重，不用恢复后的新 InstanceId 当唯一业务事件身份。若推进后 fault，accepted 保留为执行事实，但本次不形成可恢复成功检查点；记录故障尝试，从旧已提交检查点重试或终止。外部诊断费用可以单独记录，不成为成功样本。

提交后回执丢失，调用方按 commitId 查询；已提交则返回原回执，不重复推进策略。多候选胜者信息在 run 返回前丢失时，不猜测 capture 的 output 对应哪个 action；从旧检查点恢复并按登记输入顺序重新执行该未提交尝试。外部输入意图需先可靠入队。上层不从 capture 倒推非单射 respond 的原动作。

重启后恢复 artifacts/provider、checkpoint、policy/session 状态；清空原宿主绑定，读取新请求，建立旧逻辑请求到新凭证的受控映射，再继续。关闭/释放只在提交引用不再需要后执行；垃圾回收以活引用为准。

## 11. 关系估计与证据

对局关系按规则、构筑、策略、对手、座次和预算条件分组；展示胜/平/负与故障/截断各自计数。替代关系报告基准与替换的结果差，不把优势自动解释成全局卡牌强度。

主指标为胜局1、平局0.5、负局0的条件结果。干预效应以同一种子块内差值计算，座次合并规则提前登记。置信区间采用按独立种子块重采样的 bootstrap，固定分析随机种子和重复次数（默认2000）；同局决策和分支不是独立样本。报告实际完整配对数量、缺失数量及其条件，不隐藏失败导致的选择偏差。

协同/反协同通过预先登记的2×2替换实验表达：两个指定槽位分别使用候选或基准，四条件效应差计算交互。首个组合固定为基础构筑中一个火花槽替换成爆裂、一个守卫槽替换成修复；两项各为开/关形成四个合法构筑。仅在足够覆盖、规则/策略条件一致时估计；首版不做无限卡池组合枚举。克制是条件对局关系，可以形成环，不强制总排序。

最低有意义差异和最低样本阈值写在登记配置（初始绝对差0.05、完整种子块至少64）；阈值是展示/判断规则，不是功效保证。发现阶段筛选候选，独立确认集重新计算；确认阶段在读取确认数据前固定候选数量 m；采用 Bonferroni 分配后的 bootstrap 区间（分位点 0.025/m 与 1−0.025/m），重复数至少 max(2000,400m)。该区间是有限样本近似，不宣称严格覆盖保证；不足以估计尾部分位数时标未知。不能筛选后直接沿用未校正显著性。

输出状态：支持正向、支持负向、区间落入预设等价范围、未知、数据缺失、不适用。无显著差异不能标等价。边携带条件、效应量、区间、机会分母、覆盖、适应范围和证据 task/commit 引用；未完成确认仅显示探索性。

历史挑战和循环关系保留；规则/策略换版后新建结果上下文。图是关系查询的呈现，不生成手工边或最终伪数据。

## 14. 实施顺序与预算

先解决受控后端兼容/续延关卡，同时形成正式原生 runtime 和 game-host；随后完成保存、会话和两游戏；再接策略、存储/恢复、实验与分析，最后 viewer/CLI 端到端。普通实验原生路径与受控续延路径使用同源规则，最终交付两者。

初始实施顺序（已有对应实现与正式测试，不是当前待办）：解决编译库发布元数据与兼容性，再执行同源运行验证：同源程序提前编译并只装载产物，嵌套 async/递归/闭包调用 IO → 保存 → 销毁进程 → 恢复 → 输入 → 与原生轨迹比较；再加通用 benchmark、Zod 和真实斗地主。该验证先于大量 UI/分析实现，避免末期才发现执行底座不可用。

全部计算本地优先，已有 RTX4070 不作为首版脚本系统必须资源。增量计算/API 总上限 $500；初始计划外部API/付费算力为0，留出预算不等于授权购买。自动脚本止于登记预算，外部支出须符合用户具体授权。

未解决的硬风险只有受控底座的真实兼容性/效率；游戏默认规则、事务链路、模块归属及统计方法已给出实现选择，不能以风险未解决为理由偷偷只交付原生版本。若成熟候选均失败，报告具体反例和替代工作量，保持公共协议与有效需求。

## 15. 来源与适用限制

以下用于核对技术能力，不作为已经完成实现的证据：

- [EffectfulJS 官方源码与 MIT 许可](https://github.com/awto/effectfuljs)，[es-persist 说明](https://github.com/awto/effectfuljs/blob/main/packages/es-persist/README.md)：持久 async 转换；具体适用限制和安装关卡见 compiler-and-differential-spec.md。

### 主 runtime 执行约束（2026-10-11 更新）

两种执行器共享当前 Node runtime，通过普通模块工厂隔离可变模块变量。受控运行库的代码、注册表和静态元数据归共享 LoadedProgram；续延帧、闭包环境、Future 队列、依赖可变配置和预算归独立 Context；不修改宿主 Promise、Function/Array 原型或 MessagePort/MessageChannel 原型。代码产物采用编译生成的私有 CommonJS 工厂。原生构建路径通过临时模块文件加载并缓存，随后移除文件；受控路径在共享 Program 的 V8 Realm 中装载工厂及运行库。同 Program 的 Instance 共享 Realm，fork/restore 不创建 Realm。两条路径均不在运行时做 TS/Babel 源码转换。存档代码位置引用同版本静态工厂，恢复和 fork 重建独立对象图。计算预算为协作式检查，移除 vm 超时。

实验登记 checkpointEvery=0（默认）表示仅完整对局提交；正整数 N 表示每 N 个已完成决策保存检查点。受控能力本身不强制写盘。没有检查点时崩溃重跑未提交的完整局；有检查点则恢复最近的已提交现场。配置和预算一起冻结，resume 不修改频率。单 runtime 的有界并发用于交替推进，不宣称多核加速。


## 16. 后续训练闭环与全 Rust 执行后端方案（2026-10-16）

### 决策与实施时机

用户决定冻结当前 JS/COW 性能优化，先用现有框架跑通具体游戏与训练路径。原 ≤600 ms/局、峰值 RSS ≤900 MB 的优化目标未达成，不再作为进入训练阶段的前置门槛。冻结不是已验收、已提交或清理工作区的声明；实现状态和遗留试验见 plan.md。

未来高吞吐路线确定为：游戏规则、状态、推进，以及执行框架整体迁移到静态类型 Rust。范围包含 Core/Instance 生命周期、游戏绑定与推进、受控 IO、采样 worker 调度、训练观察/动作编码及数据输送；游戏内部热路径不再依赖 JS 对象模型、V8 或现有 JS 受控包装。不是仅用 Rust 包一层进程管理器，也不是只迁移 Core 而继续解释 JS 游戏。迁移后的生产游戏规则在 Rust 中维护，现有 JS 实现作为过渡和差分参考；不承诺任意 JS 程序自动转换为 Rust。

这是高成本整体重构，当前仅记录方案，不创建 Rust 工程、不迁移模块、不新增依赖、不租卡。下一阶段先确定游戏/规则版本、观察与动作表示、奖励、训练算法、模型规模和评测安排。训练策略与 GPU 张量框架可独立部署，不要求为迁移环境执行框架而重写 GPU 训练生态；展示界面也不属于此次执行后端迁移范围。

### 执行与数据表示

静态规则和代码归共享 Program，每个实例拥有独立 Context；卡牌、实体和动作使用结构体、枚举、整数 ID 及紧凑数组，通过索引/句柄表达关系。临时缓冲区复用，步骤级/对局级临时区按生命周期释放；跨 IO 状态不能因临时区重置丢失。优先减少分配次数、动态分派、通用属性表和版本包装，而非把当前 JS 元数据逐对象翻译成 Rust。

执行框架保持 Core/Instance/BaseGame 职责和既有公共协议语义。受控 IO 是框架显式提供的能力接口，随机、时间和外部输入继续经声明边界传入；批量传输与紧凑编码属于适配和传输实现，不擅自更改公共字段、动作接受语义、记录关联或可见信息。避免每一步重复经过 JS 对象、JSON、Rust 对象和张量的多轮转换；必要校验不能因追求吞吐而省略。

Rust 类型与所有权不自动提供宿主能力隔离。未来实施时需要明确自有可信规则的能力约束与不可信程序的隔离方案；若采用 Rust→Wasm，须独立验证导入白名单、内存限制、预算和恢复。Wasm 是可评估的部署方式，不是本次已经选定的依赖。

### 生命周期、保存和分支

采用常驻 worker 池：一个进程连续处理多局，状态快速重置；进程负责并行、故障隔离和有界回收，不以逐步/逐局创建与销毁进程作为主要提速手段。跨 worker 合批观察与动作，为 GPU 批量推理提供数据。单进程异步并发不等于多核吞吐。

保存边界继续为对外 IO 等待点和正常终局。Context 必须包含继续执行所需的控制状态、引用关系、待决 IO 及内侧 SDK 状态；不能只复制棋盘或牌面，也不能将原生指针、进程栈或 Rust Future 的内存字节直接当成可移植存档。续接需要编译支持或框架内部显式表示，不以要求游戏作者手写 PC 来满足既有执行要求。

fork/restore 复用 Program，不重新初始化依赖，不扫描/复制完整状态，不在首次推进补做全量复制；保持既有快速分支要求。候选实现为块/页级 COW 或持久化状态，写入只分离受影响部分。普通新局的 reset 与任意中间状态的 fork 分开设计。操作系统 fork 仍有页表、调度和写时页面分离成本；Wasm 实例池/初始镜像 COW 也不自动提供中间现场保存恢复，不能拿快速实例化替代状态分支验收。

### 性能依据与估算

现有 Forge Duel 固定 seed 991、16 局、356 个决策（不是斗地主吞吐基线，不能直接用于斗地主训练容量承诺）：受控执行阶段 30.4 步/秒、完整流程 27.3 步/秒；原生分别为 61.0 和 50.6 步/秒。测量包含现有游戏校验、边界复制和记录成本，策略为脚本，尚不含模型推理与训练。

同口径 GC 窗口内，原生/受控累计分配为 10.14/18.17 GB，GC 停顿为 114/883 ms。平均每局约 7.1/55.2 ms 停顿，说明仅去掉已记录 GC 停顿不足以解释数倍提速。Rust 的主要潜在收益还来自消除细粒度对象管理、动态属性路径及重复转换。累计分配、GC 后存活内存和峰值 RSS 必须分别报告；不把减少分配等同于同比降低 RSS。

以下是未来后端的设计目标和敏感性估算，不是 Rust 实测或性能承诺。每步包含环境推进、必要校验和训练观察编码，不含模型计算；并行假设有足够 CPU 资源、扩展效率 70%。

| 单 worker 目标 | 单 worker 吞吐 | 8 worker 估算 |
| --- | --- | --- |
| 10 ms/决策 | 100 步/秒 | 560 步/秒 |
| 5 ms/决策 | 200 步/秒 | 1,120 步/秒 |
| 2 ms/决策 | 500 步/秒 | 2,800 步/秒 |

未来首个候选验收目标为单 worker ≤5 ms/有效环境决策，8 worker ≥1,000 个有效决策/秒；必须在迁移后的具体游戏、固定硬件、相同正确性与记录要求下重测，记录批量大小、并行效率和尾延迟。不能把移除记录/校验所得收益全部归因于 Rust。

训练供数示例：2,000 万参数、128 tokens/决策、新数据训练 4 遍、有效训练算力假设 50 TFLOP/s，按 6×参数量×序列长度×遍数近似，每个新决策需 61.44 GFLOP，对应约 814 个新决策/秒。8 worker、70% 扩展效率要求单 worker 约 145 步/秒，即 ≤6.9 ms/步；5 ms 目标理论上覆盖这一计算需求。该模型、编码长度与算法尚未选定；估算未含模型推理、额外网络、IPC 和训练/采样交替等待，不能视作 GPU 利用率保证。只有部分玩家决策用于学习时，按实际有效样本率折算。

### 后续实施原则

先用当前框架确定游戏和训练接口，获得模型推理/更新、有效样本产出和学习效果的真实基线，再安排全 Rust 重构。迁移按完整游戏纵向闭环验证；对相同种子、动作和 IO 回复比较观察、合法动作、事件、接受结果、奖励、终局、快照恢复及分支行为。规则一致性、结构约束与性能分别验收。Rust 后端不适用的 JS 语言测试不能用来证明迁移正确；现有 JS 后端的未完成验收也不因此自动完成。

阶段 1 覆盖三种脚本、三座位、同策略及混合策略多局运行、各游戏阶段、种子复现、数据与终局统计、原生/受控同动作差分及记录重放。至少累计 100 局正常终局，并单列所有截断/错误。FirstLegal 可能在叫分时总选不叫，导致连续重发；应保留其定义并验证有界截断，用其他策略组合及专项夹具覆盖终局，不能为了“跑通”改脚本含义或游戏规则。脚本仅用于框架正确性验证，不证明平衡或策略强度。阶段 2 的固定对手基线优先沿用三个已验证脚本，规则型开源策略可选。

本轮读取的本机配置：arm64 Apple M5 Pro，18 个逻辑 CPU，48 GiB 内存，可用磁盘约 546 GiB。默认 Python 3.9.6 未安装 torch/numpy/rlcard；已存在 uv。实际采用本机已有 Python 3.14.6 创建隔离 .venv，uv.lock 锁定 PyTorch 2.14.1、NumPy 2.5.4 和固定提交的 DouZero；CPU 参数更新及保存恢复检查通过，MPS 未启用。

### 17.2 复用开源实现与选择

首选 [DouZero 官方仓库](https://github.com/kwai/DouZero)，本轮检出的参考提交为 `718a5c920bf3361e34178a38f3b80458e176b351`，代码许可证 Apache-2.0。复用范围为 `douzero/dmc/dmc.py` 的 Deep Monte Carlo 回归、`models.py` 的三角色 LSTM+MLP 候选动作评分结构、RMSProp/梯度裁剪及 checkpoint 思路；`evaluation/rlcard_agent.py` 提供现成规则对手来源。该规则策略还依赖 RLCard 的牌型表，且会修改传入列表、捕获异常后随机选择；接入时只给独立策略 DTO，并显式统计不支持牌型、异常与合法回退，不能把回退隐藏为正常教师决策。实际引入代码时保留上游许可证和适用的归属声明，固定来源版本。

备选 [RLCard 官方项目](https://github.com/datamllab/rlcard) 也提供 `examples/run_dmc.py`，但同样需要替换其游戏环境；首版不并行维护两个训练框架。DouZero 原模型是历史 LSTM 加候选动作 MLP，并不是 Transformer。为了先复用现成脚本闭环，本阶段先用该结构；此前小型 Transformer 方向保留为闭环后的模型替换，不作为首版前置条件，也不另写 PPO。

上游现成命令 `python3 train.py --actor_device_cpu --training_device cpu` 支持 CPU 训练，但默认总帧数极大，不能直接无预算运行。上游 `generate_eval_data.py`/`evaluate.py` 可作为其自身工具链检查，不能代替我们的完整规则评测。预训练权重不是必需品；若以后使用，另行确认下载可用性、权重使用许可及特征/规则兼容性。

关键适配差异：上游 `douzero/env/env.py` 直接给地主 20 张牌、农民各 17 张牌，从出牌开始；没有我们的叫分和加倍流程。牌型解释、倍数结算也不能假定相同。不得让 Python Env 推进正式对局，不得将上游牌型表当作我们合法性的裁判。

### 17.3 执行与训练数据路径

执行路径固定为：TS 完整 GameHost 发出玩家请求 → 玩家可见观察与 exact 合法候选编码 → 常驻 Python 策略评分 → 返回该请求的候选索引 → 原有 respond/接受流程 → TS 继续推进至终局。Python 只推理、训练和保存模型，不持有第二份权威游戏状态。模型不读 Frame.state；只使用现有 observe/projectEvent 的可见输出，包括自己的手牌和已公开信息。地主相对座位显式映射；未定地主时不提前编码未来角色，农民不共享私有手牌。

动作编码保留牌型 kind/high/length 等解释；同一组牌的不同合法解释仍是不同候选。不按花色制造冗余动作，不裁掉合法候选。上游按牌多重集输出的规则动作只能映射回 exact 候选；歧义采用固定顺序并计数，无法映射才执行已声明的合法回退。模型返回越界索引、错误请求标识等属于失败，不能靠静默随机动作掩盖。

首版采用常驻进程、带请求标识的 stdio NDJSON；每局、每步不启动新 Python。训练适配放在游戏侧及独立训练工具中，复用现有玩家接口，不向 Core/Instance/BaseGame 增加训练字段。先 1 个 TS 采样 worker、1 个 Python 服务，逐局串行采样，按第 17.6 节累计跨局批次才更新，版本切换只在完整对局之间；正确后最多启用 4 个 TS worker，Python torch 初始 2 个 CPU 计算线程，避免进程/BLAS 线程相乘。冻结教师使用独立常驻推理服务。训练数据队列有界；候选过多时分块评分而不截断。

只收集实际被接受的模型动作。农民并发请求可能产生未获接受或过期的响应，不能把全部策略调用记成 transition。请求次数、被接受动作、参与学习的出牌动作分别计数。推理墙钟耗时不自动推进游戏逻辑时钟。超时默认动作、控制输入和模型选择分别标记；故障和预算截断不能伪装成输局。完整可见历史用于编码，模型可沿用上游有限历史窗口，但必须明示这是模型特征压缩，不改变游戏历史或玩家接口。

首版采样采用原生 GameHost 加显式训练消费者；该消费者只保存学习所需的观察、选中动作及元数据，不默认开启完整执行记录。受控模式用于固定种子差分、抽样记录重放和故障复现，并单列其成本。两种模式均经过 Card Core；不创建“无 Core 原游戏”的第三条路径。

### 17.4 首版策略与学习目标

第一里程碑的完整游戏中，叫分/加倍/再加倍由固定、可复现脚本处理：轮到可叫分时选择最低合法正分，加倍和再加倍选择否。专门夹具另外覆盖全不叫重发及双方加倍。出牌由三角色模型自博弈学习，阶段 2 独立评测统一叫分/加倍脚本，再比较 First/Last/Random 的出牌策略及可选旧模型；不改变阶段 1 三个脚本的原始行为。此里程碑是“全游戏执行、仅出牌学习”，不是全阶段策略训练；不会声称训练出了叫分和倍数策略。

出牌阶段复用 DMC：终局按胜负回填每个实际接受动作，地主获胜地主 +1、两个农民各 −1，农民获胜反之；中途不造额外奖励，首版不折扣。以 MSE 拟合选中动作价值，采用 epsilon 探索，初始 epsilon 0.05、RMSProp 学习率 1e-4、梯度范数上限 40；这些是启动配置，不是最优超参结论。实际规则结算分另外报告，不能把团队胜负目标说成结算分优化。初版曾按单局 T x 1 调用 learn，现按第 17.6 节改为跨局批次；真实角色轨迹末端标记 done，终局回报回填全部出牌样本。完整对局内模型固定，不填假终局。WP 配置采用上游 epsilon 0.01。

采用上游模型结构并按本规则扩展必要可见特征和动作解释，因此不保证原权重可直接加载。候选列表只用于推理，训练缓冲保存选中动作的特征，避免把每一步所有候选常驻留存。首版不依赖人工数据或现成强模型。后续全阶段学习再加入叫分/加倍评分头、未定角色时的观察编码及对应席位终局收益；最终角色可以用于终局标签，不能泄漏进叫分时的输入。

### 17.6 预训练指导与批次修正（2026-10-18 后续授权）

新增原始 WP 模型推理与扩展模型初始化两种形式。原始模型直接对当前 exact 候选评分；扩展初始化保留兼容层，dense1 按 [LSTM 历史、原状态、新状态、原动作、新动作] 的列位置复制原权重，新增列置零。角色、卡牌映射、历史和候选按可见信息构建，Python Env 不参与正式游戏。权重来自固定提交并记录实际来源；镜像不能冒称已认证的官方原件。

完整对局内版本固定，结束后把三角色样本放入有界编码队列。每角色累计 3,200 条后调用既有 learn，真实终局标记随样本保留，不能把批次末尾伪造为终局。尾批保留到恢复；checkpoint 同时保存未消费队列、已采集/已更新计数和采样配置。采样预算按已采集样本判定，消费样本单列。旧单局 checkpoint 保持可读，不悄然丢弃队列。冻结预训练可作固定对手，按完整阵营与自博弈混合采样；只训练学生实际接受的动作。

完整阵营评测包括学生地主对两名对手农民、两名学生农民对对手地主；同 seed 的同一副牌交换两侧算法，以种子聚类统计阵营及综合胜率、规则得分和区间。旧单座位替换单独标为诊断。预训练适配、迁移等价、跨局批次、尾队列/优化器恢复与真实游戏差分进入正式检查；实际试训和至少 300 独立种子的固定对手评测完成后交付。

### 17.7 吞吐口径与 MPS 后续门槛

已测同机完整斗地主脚本基准：原生均值 27.958 ms/局、受控 34.328 ms/局，每局 68 个接受决策，折算约 2,432 / 1,981 决策每秒。这是特定脚本轨迹的游戏执行参考，未包括模型、张量编码、IPC 和参数更新，也不是不同策略下的训练吞吐上界。仅按这一原生参考摊销，100,000 个接受决策的游戏部分约 41 秒；真实训练样本只计出牌，局长与候选数也会变，不能据此承诺 41 秒完成训练。

首轮必须计量：环境/观察编码/IPC等待/候选推理/参数更新耗时，候选数量 P50/P95/max，完整局数、接受决策/秒与有效训练样本/秒，checkpoint/评测独立用时，进程组峰值 RSS、TS 分配/GC 和 Python/torch 内存分别报告。若有效采样速度实测为 50/200/500 条每秒，则 100,000 条的采样阶段分别约 33.3/8.3/3.3 分钟；这些是条件算术，不是本机实测预测，更新和评测另加。原生与受控按同样模型/种子/工作量配对比较，训练消费者成本与受控记录成本分开。

Apple GPU 仅作为 CPU 闭环后的可选加速。[PyTorch 官方 MPS 文档](https://docs.pytorch.org/docs/main/notes/mps.html) 提供可用性检测方式；DouZero 当前 device 分支只处理 CPU/CUDA，不能直接传 mps 就声称支持。需要适配设备选择并验证 LSTM 前向/反向、张量传输、checkpoint 恢复与 CPU 数值对照，再按同批次测总耗时决定是否启用。小批次 CPU 可能更快，MPS 不作为闭环成功条件。

PPO 使用完整终局轨迹的 Monte Carlo 回报：同一玩家从其最早实际接受决策到终局的效用均为 R_i；不把其他玩家的动作或无效提案拼成该玩家 transition。斗地主 score 目标定义为 tanh(规则分/12)，win 目标为最终所属阵营胜负 ±1，最终角色只用于标签；Forge 为 2×规则胜分−1（平局 0）。分数压缩是明示的风险效用，不宣称等价于最大化未压缩规则分；原始分和胜率另外报告。截断/错误不生成终局回报，不消费这些半局轨迹。

对固定采集版本 θ₀，记录实际采样 log π₀(a|o)，重算 V₀(o) 并验证 log 概率与原记录在 2×10⁻⁵ 浮点容差内一致；A=R−V₀，按整个 rollout 标准化并停止梯度。优化目标为 −mean(min(r A,clip(r,1−ε,1+ε)A)) + c_v mean((V−R)²) − c_e H(π) + c_t CE(教师候选)，r=exp(logπ−logπ₀)。默认 ε=.2、Adam 3e−4、4 epochs、minibatch32、梯度范数上限 .5。教师项可关闭，斗地主可用冻结 WP 出牌评分 argmax 和明确的前置规则标签，Forge 可用现有 rule 评分；标签来自学生实际接受时的观察与候选，绝不冒充教师实际执行的动作。自有网络负责所有实际学生决策。

采样使用稳定 exp(logit−max) 权重（差值下界 −30）；TS 将每个有限 IEEE754 权重还原为二进制整数比，借用既有 RandomCursor 做拒绝采样，返回相同权重比的 log 概率，避免固定小整数概率表舍掉合法动作。此采样正确性条件是 RandomCursor 提供约定的均匀伪随机流；机器浮点 log/softmax 的差异按上述容差验证。不将有限精度 autodiff 说成连续实数上的精确证明。随机游标和策略记忆仍只在动作实际被接受后由既有 Router 提交；Python 推理无随机抽样或跨玩家隐藏状态。

完整一局内权重冻结。累计至少 1,024 条同版本已接受 transition 后，消费整个有界 rollout 并更新，再发布新版本；未满批连同请求身份、玩家、阶段、行为版本、实际概率、候选特征及回报保存。消费后才清空队列，更新只在对局之间进行；stale/mixed/重复 request 拒绝。checkpoint 原子保存参数、Adam 状态、Torch RNG、未消费 rollout、采样/奖励配置、下一局 seed 和所有计数。恢复后以同一版本继续收集，重跑未保存完整局不重复计入已保存样本；Ctrl-C/SIGTERM 在完整对局边界保存。源码/环境标识随模型保留，模型不能静默跨游戏载入。

闭环正确性按归纳不变量验证：已有 Core 保证给定 seed/接受动作的规则轨迹；可见纯编码与完整候选不改变规则；Router 关联保证实际样本与接受动作一一对应；终局玩家标签不进入早期输入；固定版本概率验证保证更新只消费该采集策略的数据；原子模型/队列/seed 同时恢复保持累计样本=已消费+未消费。数学部分是这些条件下的轨迹和恢复一致性，不声称神经网络全局收敛或博弈最优。正式检查分别覆盖数值目标、padding/采样分布、信息隔离、真实两游戏推进、原生/受控一致、记录独立重放、队列/优化器恢复和故障停止。

### 20.3 预算与状态流

发现批次累计 64、128、256 块，追加只使用发现数据。区间宽则加局；明确候选进入确认；操作策略结论相反则保留策略依赖；使用机会与出牌差异只生成适应疑点，不自动证明策略不会玩。预算耗尽输出未决。

确认前冻结候选集合、规则、构筑、策略、环境及样本量；样本量根据发现方差和目标精度规划，单比较最多 2,048 块，并受预登记总局数上限约束。不同候选间的预算分配也在确认前固定；不足时不强行发布确定结论。发现筛选采用完整块的均值 ± 2 个经验标准误，仅挑选待确认假设，不作为最终置信结论；确认区间采用 Maurer/Pontil 有界独立样本经验 Bernstein 双侧界，按冻结候选数量分配 alpha。常量样本仍保留范围项不确定性；加权环境结论使用同时有效的分项区间加权，不独立重采样共享基准。来源：https://www.learningtheory.org/colt2009/papers/012.pdf 。种子驱动的伪随机独立对局是统计推断的采样前提，不将固定有限种子穷举误称为对全部玩法的证明。确认集使用独立种子，不用于选 checkpoint 或调参；一次正式分析控制确认集合的多重比较。不以反复查看普通置信区间后首次显著作为正式停止规则。无候选不生成确认对局。

结论包括改善、恶化、实际等效、条件依赖与未决。等效要求区间完全进入预设等效带，不把不显著当等效。沿用现有分析接口时明确区分“确认阶段”与“证据支持确定结论”。0/1 极端样本不能仅凭退化 bootstrap 区间宣称无不确定性，需采用适合有界配对块的保守区间或回退规则，并纳入正式检查。

### 20.6 确认统计的适用证明

令独立种子块 i 的座位配对差值为 Xi。比较/替换时 Xi∈[-1,1]；四条件交互时 Xi∈[-2,2]。块内同 seed 的不同构筑及座位允许相关，共享基准也允许跨比较相关。对 n 个完整块，使用样本均值和分母 n−1 的样本方差 V；范围宽度 R 分别为 2 或 4。每个确认假设的双侧半径为 sqrt(2 V log(4/αh)/n) + 7 R log(4/αh)/(3(n−1))，再截取到已知取值范围。该界保留常量观测的范围项；n<2 时使用完整范围。

发现数据可以任意决定候选与预算，但确认候选集合 H、每项样本量和实现必须在读取确认结果之前冻结。条件于这些选择，确认种子与发现数据独立且块独立同分布时，每个假设按 αh=α/|H| 使用上述界；由并集界，全部确认区间同时覆盖的概率至少为 1−α，无须假设不同假设独立。共享基准因此不能被当作新增独立样本，但也不破坏该多重比较控制。非负固定环境权重归一化后，对同时有效的分项界加权即可覆盖综合效应，不需要忽略协方差计算独立误差条。操作策略不自动加权。

只有区间完全在 +margin 以上、−margin 以下或等效带内部时，才分别输出改善、恶化或实际等效。确认阶段的结果也可能未知；confirmed 仅标记数据阶段，不表示已证明有差异。完整性不满足时禁止发布确定判断，因为丢失对局可能依赖结果。发现阶段逐批查看与经验标准误筛选不获得正式错误率保证，页面与报告必须保留发现/确认阶段标记。以上为统计模型下的条件证明，不证明固定伪随机生成器产生真独立样本，也不证明所选策略达到最优打法。

### 21.2 生产实现归属和执行路径

生产游戏新增 examples/sts，沿用 src/tests、独立 typecheck/test/check 和根 workspaces 汇总。以下为职责与建议文件组织，不为每个概念创建包：

| 文件/职责 | 内容 |
| --- | --- |
| game.types.ts / game.schemas.ts | 开局、动作、观察、结果；种子以无损字符串传入，规则内部可用 bigint |
| state.types.ts / rng.ts | 唯一领域状态、身份、所有随机流和源数值运算；不导出活动图 |
| rules.ts / resolution.ts | 源实际需要的队列与数据化效果、伤害/状态/移牌/触发等规则语义入口 |
| cards.ts / monsters.ts / relics.ts / potions.ts | 静态内容与效果程序；按规模拆具名文件，禁止向 VM 加内容判断 |

| experiment/ 与现有 CLI 接线 | First/Last/Random、单玩家观察、动作与事件交付、现有 runner 和记录 |

路径为 `STS CardDefinition → 现有 CardProgram/CardMachine → 单一 Context → 现有 Instance → BaseGame → 策略/runner`。原生/受控仅切换存储和既有能力。C++ 参考只进入 tests/reference，不成为生产依赖，不替我们的代码计算下一状态；生产运行时也不启动参考进程。生产 Frame 只构造玩家可见的稳定发布数据，GameContract 只读转发；不为了差分在每次 IO 导出 RNG、未来池、隐藏牌序或另一份世界。全量私有状态由正式测试读取实际 CardMachine Context 或已保存 Context 对照，不增加公共调试端口。

先把源规则原语逐个迁移，数值上对应，再用已证明的效果组合构造流程。C++ 的动作 lambda 改为 effectId＋捕获环境，保留按值/按引用及卡牌身份；跨房间回调改为具名效果或调用帧。需要交互的过程使用 request/invoke，不能塞在单个 operation 中，也不把整套原 C++ 循环藏进第二个解释器。

新游戏的队列、登记、触发游标、选牌中间值、长期牌与战斗副本关系及源实际需要的调度状态均在 Context。伤害、状态和动作走明确的规则函数，保留通用效果组合。规则库先服务本游戏；确认与游戏无关且有两游戏用途后才提取公共函数，不以本阶段为理由重新架构已有两款游戏，也不为未授权的未来机制增加生产字段。

### 21.3 先建立可独立运行的 C++ 参考

正式差分夹具归 examples/sts/tests/reference，不在仓库增加独立审计脚本或报告体系。准备脚本检查固定提交及依赖，缓存构建产物到忽略目录；缺源码、编译器或构建失败必须明确失败，不自动跳过。已使用 clang++ 的独立 C++17 测试目标链接完整源 src 并通过正常冒险与成功轨迹重放；无需装载 pybind11/Python。平台兼容修正若必要，限定为构建适配，逐项确认不改游戏运算/规则。

参考进程通过测试私有的结构化消息接收 start、inspect、validate、advance、close；输入输出为有明确类型的测试 DTO，不修改公共 Core 协议。它持有 GameContext 及当前 BattleContext，沿原 init/executeActions/exitBattle 路径推进，调用原 search::GameAction 和 search::Action 的校验/执行方法。两边收到同一语义动作，由各自适配器独立编码为索引/位字段或本项目动作。

现有 Python NNInterface 只提供压缩、截断的一热观察，不足以检查等价；参考导出器直接读取源状态。也不能只解析 operator<< 的调试字符串。导出器尽量只读：同一停止点连续 inspect 前后字段与 RNG 相同，证明观察未推进游戏；缺失字段要补导出，不能删除 TS 对应字段来凑一致。

参考 C++ 的 std::function 不要求也不能用函数指针地址跨语言比较。稳定边界先比较全部语义状态和待决选择；对尚未执行的闭包/队列，按源位置维护捕获映射并使用定向续跑检查。需要定位首处分歧时，在测试构建中加入只读源位置/动作顺序追踪，不能改变随机调用、捕获和结算顺序。此追踪不成为生产事件协议。

### 21.4 差分标签、状态关系及合法动作

以每次可交互停止边界为主切点：开局选择、地图选路、事件、奖励、Boss 遗物、牌选择、宝箱、休息、商店、战斗行动及终局。在两边先对齐相同边界，比较当前状态与合法动作，再选一项动作交给两边，继续到下一边界；任一侧多出/少了选择立即失败，不靠重新挑动作恢复同步。

| 对象 | 必较内容 |
| --- | --- |
| 完整冒险 | 章节/楼层/房间、地图节点与边、钥匙、血量/金币、牌组、遗物及计数、药水、奖励/商店/事件候选和进度、后续会影响执行的标志 |
| 完整战斗 | 行动方与阶段、回合进度、能量/格挡/生命、敌人身份/意图/历史/状态、各牌堆及顺序、牌升级/费用/临时值/永久值、部分选择、实际队列语义与续接义务 |
| 随机 | 每个随机流的状态和计数，含战斗入场重播种与退出回写；每次使用的流、调用次数和结果 |
| 交互 | 请求类别、候选顺序、可选数量、动作语义、接受/拒绝、可比较的领域事件及结果 |
| 终局 | 源原始 outcome、触发原因、章节/钥匙/心脏状态；正常死亡、目标成功、未达目标、资源保护分别对应 |

C++ enum/索引与 TS 业务身份使用明确映射，保留重复对象的对应关系、牌堆顺序及动态身份。公共随机凭证允许双射；业务 ID 不能无条件清空，数组不能排序后再比较。不同的内部布局不强求字节相等，比较关系必须保留未来行为，不能只比较血量和胜负。

64 位整数用十进制字符串或固定字表示跨进程值，避免 JS Number 精度丢失。按源语义实现有界抽样、shuffle、float 与溢出，关键中间值按浮点位模式核对；不加宽泛 epsilon 让差分通过。编译时固定精度相关选项，不启用改变语义的 fast-math。源行为若依赖未定义行为或跨编译器不稳定，先构造最小反例定位，不把结果随机接受。

合法动作分开核对校验器与枚举器。已知 EXHAUST_MANY/GAMBLE 上游搜索枚举器只给空集，参考适配器应根据选择域生成候选并调用原 isValidAction 校验，建立完整可执行动作域；原搜索枚举结果另外作为已知不足的反例。该增强不改源状态转移。双方按同一语义动作配对，明确记录原枚举器与完整域的差异，不谎称原枚举集合与新集合完全相同。有限多选域穷举，普通动作包含出牌目标、药水、结束回合、跳过/拒绝奖励等。

C++ 没有与我们的全部端口事件逐项对应的日志，因此完整跨语言差分以源能独立导出的领域变化与选择为准；新增 UI 事件要有单独期望。我们的原生/受控则必须比较完整端口、BaseGame 观察、选项、接受、事件及终局；不能用 C++ 缺事件作为省略自有两模式事件比较的理由。

### 21.5 已知缺口和差异的处理

所有差异都落实为模块正式测试中的具体场景和期望，不建立另一个覆盖率账本，也不允许一个通用 ignore 列表吞掉失败。

| 差异类别 | 处理及验收口径 |
| --- | --- |
| 已有源规则、没有修正需求 | 严格比较源状态转移，未解释差异为 0；意图、卡牌、遗物等普通行为均适用 |
| 搜索枚举不完整、源校验/执行支持 | 保持原执行器，用参考适配器补全候选；同时验证新增候选能被源接受并产生同状态 |
| 源明确禁用或尚未实现内容 | 不以空效果冒充复刻成功；基线保留该范围，并明确内容缺口；新增内容使用独立规则期望 |
| 已证实源规则错误或资源保护混同输局 | 先保留原始输出与触发原因；兼容性场景精确复现上游，修正场景显式断言预期差异。生产结果不将预算/保护截断计作死亡；两种期望不得混成全字段完全一致 |

兼容性场景如需旧保护行为，使用同一规则程序的测试专用定义/规则配置，不增加公共 runtime 开关或另一套正式游戏循环。对于原作错误但尚无独立正确规则依据的情况，不能凭直觉顺手修复并要求 difftest 接受；先确定修正规范。

当前迁移已确认并保留的源行为包括：COMBUST/BRUTALITY 的颜色表为 GREEN（仍按实际铁甲牌池收录）、Deck::anyCardBottled 的反向判定及 Neow TRANSFORM_TWO_CARDS 的额外诅咒。不按商业游戏印象静默纠正。另一个源缺口是 returnRandomRelic 在池耗尽时可能使用未初始化的池指针；在确定独立修正规则前，TS 明确抛出错误，不产生替代奖励或规则死亡，此分支仍是未完成差异处理。

因此发布结果要明确“严格基线差分、已知修正测试”各自通过范围。完整参考复刻不能把未通过的普通场景降级为修正场景。读取不到关键内部字段也不算已证等价，应补参考导出或针对续接建立额外测试。

### 21.7 正式验收规模与可复现路径

主验收对象是铁甲战士 A20 碎心成功轨迹，先冻结第一条，再补到至少 3 个不同种子。优先检查能拿到的已有轨迹是否包含完整 setup、逐步动作和终局，且能在固定提交正常开局原样重放；只有 seed、胜利截图、战报、局中存档或不匹配版本的记录不能直接充当完整动作夹具。若没有可直接验证的轨迹，转入主动搜索/逐步打法；寻找外部轨迹不能成为无限等待实施的理由。

主动打法由两部分组成：战斗复用上游 BattleScumSearcher2，从当前战斗状态搜索，每次只提交一个已校验动作，再观察真实执行后的状态重新规划；非战斗由代理检查地图、血量、牌组和奖励，决定路线、选牌、删牌、升级、休息、药水与商店。可评估多条合法候选在参考副本中的后果；回退和换线后每条候选都必须从同一真实 setup 完整独立重放，不能从失败分支拼接一个不可达成功现场。

不能直接调用 ScumSearchAgent2.playout 期待碎心：源码的 MAP_SCREEN 默认走 stepRandom，营火策略没有专门规划 recall，奖励策略优先拿遗物，未建立三钥匙目标。测试动作生成器必须按可达地图规划燃烧精英拿绿钥匙、在营火保留并选择 recall 拿红钥匙、宝箱奖励中明确拿蓝钥匙；同时考虑血量、战斗和发育，允许重新规划。取钥匙只提交原合法动作，不能直接写 key 字段。三幕与 A20 双 Boss 后必须实际进入第四幕、完成精英和心脏战，不能把 Act 3 PLAYER_VICTORY 当作成功。

战斗搜索在 C++ 副本上进行，提交动作前后检查搜索没有消耗活动游戏的 RNG 或改变状态。固定搜索器自身 seed、每次模拟次数和停止预算；先以有限预算试打，卡在致命战时提高预算或从较早的合法选择重新规划。使用其已知 RNG 的搜索是用户授权的测试打法，不声称公平策略棋力，也不为生产 Core/训练增加搜索功能。记录尝试种子、失败原因与实际成本，不承诺默认参数自然能碎心；未取得成功轨迹则主目标保持未完成。

每条冻结成功夹具保存固定参考身份、铁甲/A20/正常开局条件、无损 seed、完整跨战斗与非战斗动作及其边界类型。动作编号必须区分 battle/game 的编码上下文，并保留药水目标、多选和重复牌身份。用独立参考进程从开局验证整条动作带：全部动作合法、边界相同、三钥匙齐全、A20 双 Boss/第四幕经过且心脏正常死亡。验证通过才作为可提交的模块功能测试夹具，不保存另一个验收日志体系。之后 C++、原生和受控分别从 setup 消费同一动作，执行状态完全由各自代码计算。任何三方差分都先定位实现，不修改成功动作带来绕开缺陷。

### 23.5 性能协议：先定口径，最后一批执行

新增正式 `examples/sts/tests/performance.ts` 与测试侧 `tests/reference/raw-benchmark.cpp`，在 STS package 注册 `performance:acceptance`；不创建仓库外长期维护的另一套基准执行器。复用现有参考构建配置和生产 loader/binder，采样配置在实现前确定。

1. 固定机器、Node/V8、C++编译器/参数、规则提交、构建产物和三条夹具。沿用 C++ -O2、无LTO的原生口径；参考构建只链接固定规则源码。关闭本任务其他重负载，不并行跑正确性套件、训练或 profile。
2. Program装配/加载和夹具读取单列冷启动耗时，warm测量中共享已装载 Program。每次整局计时必须包含新Context/初始化、正常全部动作、必要观察/合法域/事件/终局、正常关闭及本次持有资源释放；不复用上一局可变状态。
3. C++原生每seed按7批×10,000整局记录批均值，结果与动作/终局校验防止空跑。明确它不包含逐步JSON/IPC/公开投影，不能混称完整框架成本。带适配器的C++耗时另列，绝不用它替换20–50×的分母。
4. TS每seed、每默认模式预热5整局，然后7批×16整局；原生/受控批次交错，逐局记录耗时。报告批均值的中位数、逐局p95、总耗时和动作数。只执行这组事先约定的统计重复，不在每轮编辑后重跑。
5. 每seed、每模式的完整GameHost中位整局耗时 / 同seed C++原生批均值中位数 ≤50，争取≤20；不得只对三seed加权平均过线。p95、冷启动和初始化单列，不能仅展示最优样本。已有0.138597ms只是预算参考，最终分母随同批实测报告。
6. 测试驱动中的oracle比较、文件IO和全量私有状态检查不进入纯性能计时；正常生产合法性、观察、事件交付和默认受控记录全部在计时内。操作带只是正常玩家回调的选择输入，不能把中间状态、抽牌结果或奖励预计算进程序。

8. 某seed/模式墙钟超过60秒即停止该采样组并标记“未完成/未达标”，保留已取得样本，不更改次数、预热或分母挑选好结果。首次运行过慢时不能让112局循环无界消耗。中断和超时不算通过。
