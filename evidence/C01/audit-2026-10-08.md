# Bear Forge 斗地主与协议复核报告

日期：2026-10-08。审计对象：本地工作区的协议与斗地主源码，包含未提交文件；Git HEAD 为 `fb172c05430441d5457dc5ffe0062a73bc522124`，不能用该提交独自还原本次对象。文件摘要见 [audit-manifest.json](audit-manifest.json)。

## 结论

1. **三人游戏规则已实现，并通过补充整局检查；三人通过正式 Session/Runner/Policy 协作尚未实现、也未验证。** 两者必须分别记账。
2. **协议覆盖不完整。** 当前游戏确实使用公开作者接口，但限时调度、策略查询服务还有必须补齐的接口连接；训练/分析适配器的可调用契约也未固定。不能承诺其他模块只照当前协议实现，就自然接通。
3. **现有检查未发现合法对局路径中的确定性规则错误，但发现了帧一致性与错误分类问题。** 122 项原测试全部通过不能推出实现无问题。本轮增加 57 次整局执行及 93,769 个牌张子多重集核对，仍不构成所有局面的正确性证明。

本轮只审计、增加复核证据并更正验收状态；未修改生产游戏/协议代码，未实现后续底座，未提交或推送。

## 二、协议覆盖

仓库共 14 组、67 个操作。操作级 schema 测试覆盖消息形状，不等于 67 个操作已有 provider。

| 边界 | 实际消费/实现 | 缺少的验证 |
| --- | --- | --- |
| GameDefinition.program | 真实 async 游戏程序经测试 toolkit 完整执行 | ExecutionPort 的装载、推进与故障处理 |
| ProgramToolkit.request/randomInt | 游戏真实调用，测试 peer 应答 | 真实运行底座、随机流保存与受控构建 |
| ProgramToolkit.record | 定义了契约；斗地主用 boundary.records 记录，未调用此口 | 通用 record 实现；不能重复追加领域记录 |
| GameModule.validate/view/actions/reward/facts | 5 个游戏钩子都有实现；本次均调用 | 和真实 GameDriver 的连接 |
| GamePort | 8 个操作只有契约 | provider、实例引用、保存与恢复 |
| Session/SessionAdmin | 11 个操作只有契约 | 鉴权、时间排序、提交、回执、恢复 |
| Policy/Runner | 10 个操作只有契约 | 独立策略调用、服务绑定、记忆提交 |
| Execution/Branch/Store | 14 个操作只有契约 | 真实运行、分支隔离、事务与故障恢复 |
| Experiment/Training/Planning/Analysis | 16 个操作只有契约 | 调度、轨迹、学习、假设模拟、关系估计 |

已遵守的边界：游戏拥有规则、循环、牌型、领域状态与投影；Core 契约没有斗地主语义；游戏没有直接调用 Session/Policy/Store；动画没有参与权威推进；保存能力 manifest 未虚报支持。

依赖检查通过的是现有源码的导入边界，不是完整的受控 TS 编译或传递依赖安全证明。后者仍属 C02。

## 三、需处理的发现

### F1 · P1 · 通用宿主没有从 deadline 构造超时输入的固定方法

位置：`packages/contracts/src/game.ts:15` 的 DeadlineSchema、`packages/contracts/src/authoring.ts:17` 的 GameModuleApi；实际消费在 `games/doudizhu/src/rules.ts:50` 附近。

deadline 只有时间、同刻优先级、timeoutRule 字符串；stage.hostInputs 只有输入类型字符串。斗地主要求的输入却是 `inputType:'timeout'` 加上带游戏 schema 的 `{slotId}` payload。公开作者钩子没有“生成到期输入”，也没有 timeoutRule 的注册/解析契约。

本次全超时对局能成功，是测试 peer 知道要调用 `pack('timeout', {slotId})`。这验证了规则的超时处理，却暴露出通用 Session 仅凭公共声明无法构造该输入。schemas 注册表说明数据如何验证，不说明应该挑哪个 schema、如何填值。

建议：在公开契约中择一固定“slot 携带到期输入模板”或“Game 提供到期输入生成钩子”，明确失效和重排语义。尤其两个 slot 同时到期时，第一笔提交会更新 boundaryKey，第二笔到期输入必须重新针对当前边界生成。默认出什么牌仍由游戏决定。

验收：不知道斗地主 schema 名称的通用调用方，只依赖正式接口，把双方超时和动作/超时同刻竞争跑通。禁止在 Session 里写斗地主分支。

### F2 · P1 · 策略拿到 actionsRef，但没有公开调用协议

位置：`packages/contracts/src/policy.ts:19–22`；对照 `session.ts` 的 SessionApi.actions 和 `planning.ts` 的 PlanningApi。

PolicyInput 提供 actionsRef/planningRef 字符串，却未定义以该引用发起调用的端口或注入服务契约。Session.actions 需要 session、auth、ticket；当前没有定义 actionsRef 如何绑定到这些权限，也没有定义策略可用的调用入口。规划引用有同样的绑定问题。

本次和既有测试直接从可信 peer 调用 GameModule.actions，因此没有穿过这段缺口。未来策略若靠全局注册表、额外闭包或私有服务接口补齐，就违反“不得自建旁路”的要求。

建议：固定受限策略服务端口，说明引用的签发者、席位/请求作用域、失效条件和调用签名；实现可以继续后置。

验收：一个只接收 PolicyInput 与正式注入能力的 LastLegal 策略可查询并出牌；复用另一席位或旧请求引用会被拒绝。

### F3 · P2 · 游戏语义适配器仍只有产物引用，缺少作者契约

位置：`training.ts:8,26`、`analysis.ts:26`、`authoring.ts:21–22`、`game.ts` 的 GameApi。

Training/Analysis 指定 reward、encoder、gameAdapter 等 ArtifactRef，但未定义这些游戏插件本身的装载入口及输入输出。GameModule.reward 需要私有 frame，GamePort 没有导出它；当前 docs 说终局按 end 一次结算，但没有固定从合法记录调用奖励适配器的契约。facts 当前返回原始审计事件，也不等于分析层已经获得机会分母、实体和条件关系的定义。

斗地主公开 result 含三人分数，技术上可以据此构造奖励，所以这不是“无法训练”。问题是要避免 Training 硬编码斗地主 result 或私自索取 GameFrame。

建议：固定离线奖励/分析适配器的公共作者入口及数据权限；训练算法和关系估计实现可后置。上线前必须证明三个 actor 都能得到一次终局结算，未再行动的农民也不遗漏。

### F4 · P2 · Policy.release 的实例标识没有来源

位置：`packages/contracts/src/policy.ts:24–27`。

release 要求 policyInstanceId，但 describe/decide 均不创建或返回该 ID，PolicyBinding 也没有这个字段。单靠目前协议无法完整实现实例释放与复用边界。

建议：先决定是否存在有生命周期的策略实例。如果存在，补正式创建/绑定/释放契约；若完全由显式输入携带状态，则改为具有明确资源作用域的释放方式。

### F5 · P2 · 终局 frame 内部结果矛盾仍被接受，已复现

位置：`games/doudizhu/src/hooks.ts:11–15,76–79`。

复现：真实对局结束后，仅把 `boundary.result.scores['0']` 加 1，保留 `state.result`。reward 仍返回成功并输出旧分数；boundary.result 则给出新分数。stateOf 只校验等待阶段和终局阶段匹配，没有检查两份结果相等。该反例记录在 audit-probes.log。

影响：若可信适配器、恢复或数据拼装出了错，前端结果和训练奖励可能分歧而未被识别。当前合法游戏循环未观察到产生这种帧；这是可信边界的一致性缺陷，不是已经证明的玩家作弊漏洞。

建议：明确结果唯一来源，或验证终局副本一致、ended 必有 result。相同原则用于 slotDelta 等重复表达的数据，不要求 Core 理解游戏语义。

### F6 · P2 · 输出校验失败被误标为玩家输入拒绝

位置：`games/doudizhu/src/hooks.ts:25–30`。

implement 把请求解析、钩子执行、响应解析放在一个 try 中，并把所有 ZodError 归为 rejected。若钩子自身生成非法输出，response.parse 的错误也会变成 invalid_game_input，掩盖实现故障。

这是由错误分支直接确定的分类问题；本轮没有发现正常对局触发该分支的输出错误。建议分开输入校验与执行/输出校验，后者归 fault，并以故障注入验证。

## 四、规则与实现核对的证据

规则基线沿用 docs/doudizhu.md 的 `competitive-2016-bear-1`，依据《竞技二打一扑克竞赛规则》2016-02 版及文档明确列出的解释/补充。报告不把其他平台的抢地主、癞子等变体混入此版本，也未重新做逐条外部规则审校。

原有测试本次重跑结果：122 passed、0 failed、0 skipped；类型检查、源码依赖边界、游戏身份摘要检查通过。

本次独立审计脚本补充：

- 48 次完整对局：3 种地主座次 × 4 种农民加倍组合 × 2 种再加倍配置 × 2 种提交顺序。无人加倍时跳过再加倍，两种配置在该情况下等效。
- 3 次完整对局：叫 3 分后，后续每一步只提交正式 host timeout 输入；验证加倍默认值、最低单牌引牌、跟牌过牌直至结算。再加倍超时已有原单元测试，本次这 3 局不经过再加倍阶段。
- 3 次交错执行与 3 次顺序执行逐项比较，共 6 次；总计 57 次完整程序执行，不表示 57 个独立随机样本。
- 每个等待帧验证三个玩家的投影、facts 与边界记录一致；拒绝上一动作重放；整局边界增量拼接等于游戏事件历史；终局每席位 reward 等于结算分数。
- 新增 3 副 17/20 张手牌，穷举 93,769 个非空点数子多重集，与已有独立 oracle 核对完整可出动作集合。覆盖长飞机、双翼、多个炸弹、2 和大小王等组合。
- 帧结果冲突反例确实被错误接受。审计脚本对此“已发现的现状”作断言以保留复现，脚本退出 0 不能解释成该缺陷已修复。

局限：oracle 虽不调用生产识别器，但仍来自同一项目，可能共享规则解释错误；这些是指定手牌和指定策略的检查，没有遍历全游戏状态，也没有和外部成熟斗地主实现做差分。测试 RNG 是确定性测试替身，不证明洗牌统计公平。未做性能 bench。
